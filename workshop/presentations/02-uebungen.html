Block 2 · Übung 4 ⏱️ 20 min

Mass-Mode: Red → Fix → Green

Den Workflow auf alle verbleibenden Bugs in Utils.cs anwenden

Ziel: Sehen, wie der Single-Bug-Workflow aus Übung 2/3 sich skaliert — alle Bug-Hunt-Erkenntnisse auf einmal in Tests gießen, dann fixen.
  1. Mass-Red: für ALLE in Übung 2 gefundenen Bugs (außer FindMax) failing Tests in einem Rutsch schreiben lassen
  2. dotnet test → mehrere Tests müssen rot sein
  3. Fix-Schleife: Bug für Bug fixen lassen, jeweils kurz Diff reviewen
  4. Green: dotnet test → alle grün. Optional Refactor (RemoveDuplicates auf O(n))
  5. Pro Bug einen Commit (4 Commits) — ihr committet, Agent schlägt nur Messages vor
# Mass-Red: alle failing Tests auf einmal Erstelle FAILING xUnit-Tests mit FluentAssertions für alle Bugs aus Übung 2, die noch offen sind (FindMax ist gefixt). Mindestens: - ParseJson<T> wirft bei malformed JSON - RemoveDuplicates ist O(n²) — Stopwatch-Vergleichstest mit großer Liste - ValidateEmail akzeptiert ungültige Adressen - CalculateAge falsch wenn Geburtstag dieses Jahr noch nicht war Naming: Should_X_When_Y. Alle Tests in tests/Utils.Tests/UtilsTests.cs. Lass alle Tests rot bleiben — KEIN Code-Fix. # Fix-Schleife: Bug für Bug Fixe jetzt die Bugs nacheinander. Stop nach JEDEM Bug. Schlag mir Commit-Message vor, ich committe selbst. Reihenfolge: ParseJson → CalculateAge → ValidateEmail → RemoveDuplicates (RemoveDuplicates auf HashSet refactoren, Performance-Test muss grün werden)
🎯 Lehr-Pointe: Mass-Red → Single-Fix-Schleife ist ein typisches Brownfield-Pattern. Schreiben aller Akzeptanz-Tests in einem Schritt = klarer Definition-of-Done. Dann fixt man sequenziell mit Sicherheitsnetz.
Fertig wenn: Alle 4 Tests grün, 4 saubere Commits im Branch, RemoveDuplicates auf O(n) refactored.

→ Pattern 3: Sub-Agents

Block 4 · Pattern 3 ⏱️ 15 min

Sub-Agent Pattern

Spezialist statt Generalist — Rolle + Kontext einengen

Ziel: Mehrere unabhängige Aufgaben parallel an Subagents geben (eine Aufgabe = ein Agent).
  1. Aufgabe in 3 Teilaufgaben zerlegen (z. B. „prüfe Tests", „prüfe Doku", „prüfe Performance")
  2. Jeweils ein Subagent-Aufruf mit klarer Rolle
  3. Ergebnisse zusammenfügen
  4. Beobachten: jeder Subagent hat eigenen Kontext, keine Interferenzen
Starte 3 Subagents parallel: - Agent A: prüfe alle Tests in tests/ auf Lücken - Agent B: prüfe Doku in src/ auf Vollständigkeit - Agent C: finde langsame Stellen mit BenchmarkDotNet Fasse die Ergebnisse zusammen.
💡 Hinweis: SPS/Motion-Folks — auch hier funktioniert das Pattern. Der Subagent kann Codesys-Export prüfen, ein anderer TIA-DLL-API. Egal welche Toolchain.
Fertig wenn: Mind. 3 Subagent-Aufrufe gestartet, Ergebnisse vorhanden.

Block 6 · Phase 3 · Stretch ⏱️ 15 min

Stretch: Stufen ④ + ⑤ — Implement & Review

Pipeline vollständig durchlaufen — Code, Tests, MR-Body. Mensch macht den Commit.

Ziel: Mit den drei Vor-Dokumenten (briefing/plan/test-plan) Code+Tests erzeugen und einen reviewfähigen MR-Body bekommen — ohne dass die Pipeline auto-committet.
💡 /implement und /review liegen schon in .opencode/commands/. Beide lesen die Vor-Dokumente automatisch — ihr müsst nur auslösen und reviewen.
  1. Sicherstellen: briefing.md + plan.md + test-plan.md liegen im Aufgaben-Verzeichnis
  2. /implement auslösen — produziert Code + Tests, fasst nur Dateien aus plan.md an
  3. Tests laufen lassen, Diff lesen
  4. /review auslösen — produziert COMMIT_MSG.txt + MR_BODY.md
  5. Mensch macht den Commit selbst mit der vorgeschlagenen Message
# Stufe ④ — Implement (Red → Green → Clean) $ opencode-cli run "/implement" # Output: Diff (Code + Tests). Nur Dateien aus plan.md werden angefasst. $ dotnet test # Erwartung: alle grün. Wenn rot → ABBRECHEN, plan.md schärfen. $ git diff --stat # Sanity: keine fremden Dateien? Größe wie erwartet? # Stufe ⑤ — Review (kein Commit, nur Vorschlag) $ opencode-cli run "/review" # Output: COMMIT_MSG.txt + MR_BODY.md # Mensch-Gate: Ihr commitet, nicht der Agent. $ git add <files-aus-plan.md> $ git commit -F COMMIT_MSG.txt
⚠️ Auto-Commit-Verbot ist eure interne Compliance-Policy (Risikobeurteilung gegen unkontrollierte KI-Commits). Auch /review committet nicht — er schreibt nur COMMIT_MSG.txt, ihr führt git commit selbst aus.
Fertig wenn: Tests grün & Diff hält sich an plan.md & ihr habt selbst committed mit der vorgeschlagenen Message. Oder: klar dokumentiert, woran es gescheitert ist.

Block 7 ⏱️ 60 min

Pipeline gegen reale Aufgabe

Selbes Repo wie Block 5+6. Bonus: lasst OpenCode sich selbst einen /pipeline-Orchestrator schreiben, der die 5 Stufen als Subagents kettet.

Ziel: Aus den Einzel-Commands aus Block 6 wird ein einziger /pipeline-Command, der die Stufen ①–⑤ hintereinander als Subagents ausführt — mit Mensch-Gates dazwischen. OpenCode schreibt euch diesen Command selbst.
💡 Meta-Übung: Ihr fragt OpenCode nicht nach dem Code, sondern nach dem Command, der den Code orchestriert. Der Agent baut sein eigenes Werkzeug. Subagents bekommen jeweils ein eigenes Kontextfenster — jede Stufe arbeitet sauber isoliert, statt einen gigantischen Kontext durchzuschleppen.
  1. OpenCode bitten, eine Datei .opencode/commands/pipeline.md anzulegen, die /context → /plan → /test-plan → /implement → /review sequenziell als Subagents aufruft, mit Stop-Punkt nach jeder Stufe für Mensch-Review
  2. Resultat reviewen: ruft der Command wirklich Subagents auf? Sind die Mensch-Gates drin? Bricht er bei Fehlern ab?
  3. /pipeline gegen eure mitgebrachte Aufgabe laufen lassen
  4. Pro Stufen-Gate: 30–60 Sekunden lesen, dann continue oder stop
# Schritt 1 — OpenCode baut sich seinen eigenen Pipeline-Command $ opencode-cli > Lege .opencode/commands/pipeline.md an. Der Command soll die fünf bestehenden Commands /context /plan /test-plan /implement /review hintereinander aufrufen — jede Stufe als eigener Subagent mit isoliertem Kontext. Zwischen den Stufen jeweils ein Mensch-Gate (continue / stop), und Abbruch wenn eine Stufe fehlschlägt. # Schritt 2 — kurz reviewen, was der Agent geschrieben hat $ less .opencode/commands/pipeline.md # Schritt 3 — Pipeline gegen eure echte Aufgabe $ opencode-cli run "/pipeline Ticket-1234: [Kurzbeschreibung]" # Pro Stufe wird ein Subagent gestartet. Output liegt im # Aufgaben-Verzeichnis: briefing.md / plan.md / test-plan.md / Diff / MR_BODY.md # Falls keine Zeit für /pipeline: Stufen einzeln durchlaufen wie Block 6
⚠️ Subagent-Vorteil: jede Stufe startet mit frischem Kontext — der /implement-Subagent wird nicht von der gesamten Briefing-Diskussion belastet, sondern liest nur, was er braucht. Das skaliert besser und produziert deterministischere Outputs.
Fertig wenn: .opencode/commands/pipeline.md existiert & briefing.md + plan.md + test-plan.md liegen vor & jedes ist auf ai_docs/ zurückführbar — oder dokumentiert, woran es gescheitert ist.

Block 7 · Abschluss ⏱️ 20 min

Stufe ⑥ — Retro & ai_docs/-Update

Session-close light: die Lernschleife schließen, sonst stagniert ai_docs/.

Ziel: Die Korrekturen aus diesem Pipeline-Lauf in konkrete Patches an ai_docs/ übersetzen — damit die KI beim nächsten Lauf weniger halluziniert und ihr nicht zweimal dieselbe Korrektur tippt.
💡 Kein Commit, kein Push, kein Tag. /retro schreibt nur einen Report und Patch-Vorschläge. Ihr entscheidet pro Patch: übernehmen / anpassen / ablehnen, dann committet ihr ai_docs/ selbst — separat vom Aufgaben-Commit aus Stufe ⑤.

Drei Reflexions-Fragen (5 min Team):

1. Lücke

Was musste der Mensch der KI sagen, was nicht in ai_docs/ stand? → DOMAIN_KNOWLEDGE.md

2. Halluzination

Was hat die KI vorgeschlagen, das wir verworfen haben? → GOTCHAS.md

3. Unklarheit

Welche Konvention musste mehrfach erklärt werden? → CONVENTIONS.md

# Stufe ⑥ — Retro (liest Pipeline-Artefakte + ai_docs/ automatisch) $ opencode-cli run "/retro" # Output: retro-report.md + ai_docs-patches.md # Team reviewt Patch für Patch — übernehmen / anpassen / ablehnen $ less ai_docs-patches.md # Mensch wendet die übernommenen Patches selbst an $ $EDITOR ai_docs/DOMAIN_KNOWLEDGE.md $ $EDITOR ai_docs/GOTCHAS.md # Separater Commit — macht ai_docs-Wachstum in der Git-Historie sichtbar $ git add ai_docs/ && git commit -m "docs(ai_docs): Lernen aus Ticket-1234"
⚠️ „Funktioniert super!" ist als Retro-Output wertlos. Wenn alles gut lief, schreibt warum — das ist auch ai_docs/-würdig.
Fertig wenn: 2–3 Patches an ai_docs/ committed sind — oder bewusst dokumentiert, warum kein Patch reinging (auch valid).
